# EXP-001 — RSI reversal + MACD confirmation — HOLD

**Date:** 2026-09-12
**Registry item:** EXP-001 (first `queued` item, taken in registry order)
**Status:** `hold`

## Hypothesis under test (unchanged from registry)

RSI reversal plus MACD confirmation improves entry quality.

Fixed candidate rule (pre-registered, not retuned here):
- Long: RSI recovers above 40 after dipping below 40 within the prior 10 bars,
  and the MACD line crosses above its signal line.
- Short: mirror condition (RSI rises above 60 then falls back below 60 within
  10 bars, MACD line crosses below signal).

No variant of this rule was run. This note only reports on whether the
existing infrastructure can produce a valid result for it.

## What was inspected

- `run_cost_adjusted_backtest.py` — the repo's existing normalized,
  cost-adjusted backtest (IS/OOS split, 3 cost scenarios, Reality Check
  multiple-testing correction). Latest recorded run: `data/cost_adjusted_backtest_latest.json`
  (`generated_at: 2026-08-24T18:57:01Z`, `lookback_days: 180`, `oos_fraction: 0.3`).
- `modules/backtest.py` — the trade-simulation engine it calls.
- `modules/backtest_costs.py` — pip/R/JPY conversion and the three cost
  scenarios (conservative ×1.0, standard ×1.3, adverse ×2.5 of quoted spread).
- `modules/reality_check.py` — White's Reality Check implementation used for
  the multiple-testing adjustment.
- `signal_scanner.fetch_history_with_dates()` — the price feed both the
  production scanner and the backtest engine use.
- `data/usdjpy_daily.csv` — the longest local price history in the repo
  (2004-12-31 through 2026-09-11, 5,556 rows), as a check on whether richer
  (OHLC/intraday) data exists anywhere in-repo that the live fetcher's
  `days` parameter simply isn't requesting.

## Missing prerequisites for a valid cost-inclusive rolling OOS test

1. **No OHLC/intraday data anywhere in the pipeline.** Both the live fetcher
   (`fetch_history_with_dates`, Frankfurter/ECB daily reference rate) and the
   only long-history local file (`data/usdjpy_daily.csv`) store exactly one
   `(date, price)` per day — no open/high/low, no intraday timestamps. This
   is not a `days=` parameter limitation; it is the shape of the data source
   itself, confirmed by the CSV's own header (`date,price`) over 21+ years.
   `modules/backtest.py` therefore resolves TP1/TP2/TP3/SL against a single
   daily close, checked in a fixed priority order (SL, then TP3, TP2, TP1).
   When a rule's stop and target would both fall inside one day's range —
   plausible for an RSI/MACD rule with intraday-scale ATR stops — the engine
   cannot determine which was actually touched first, or whether the day
   gapped through both. This is a data source limitation, not a coding gap:
   there is no historical bid/ask or OHLC feed configured anywhere in the
   project to fix it with more engineering.

2. **No rolling walk-forward exists; only a single static IS/OOS split.**
   A repo-wide search for rolling/walk-forward logic (`grep -rn
   "rolling|walk.forward|walk_forward"`) turns up only this backtest's own
   70/30 IS/OOS split (`OOS_FRACTION = 0.3` in `run_cost_adjusted_backtest.py`),
   which the file's own comments label "ウォークフォワード" but which is one
   fixed-point split, not multiple sequential/expanding folds. The
   pre-registration in `CLAUDE.md` and this run's instructions both call for
   a *rolling* out-of-sample test specifically (to avoid picking one lucky
   split), which nothing in the codebase currently implements.

3. **Sample size cannot support rolling folds even if one were built.**
   The latest recorded run (180-day lookback out of 280 fetched days, 30%
   OOS) produced OOS windows of ~76–84 calendar days per pair, with **6–8
   closed trades per pair** in that single OOS window, and the aggregate
   Reality Check ran on only 76 daily observations. Slicing that same data
   into multiple rolling OOS folds (as required for a genuine rolling test)
   would leave individual folds with 0–3 trades — too few for any of the
   three cost scenarios, let alone a bootstrap-based multiple-testing
   correction, to say anything meaningful. Fetching more calendar days from
   the same daily-close source would help sample size but does not fix
   prerequisite (1).

## What would need to change before this can move to `running`

- A price feed with real OHLC (or at minimum intraday high/low) for the
  pairs under test, so SL/TP execution order within a bar is determinable
  rather than assumed.
- A rolling or expanding-window walk-forward harness (multiple sequential
  OOS folds with a fixed, pre-registered fold width and step), built as a
  research-local script, reusing `modules/backtest_costs.py` and
  `modules/reality_check.py` for cost adjustment and multiple-testing
  correction.
- Enough historical bars that each rolling fold clears a minimum trade count
  (to be fixed in the next pre-registration, not chosen post hoc) under all
  three cost scenarios.
